# 04. AI 协作流程（怎么用 AI，怎么验证 AI）

> 面试官最关心的：你会用 AI，但你会验证 AI 吗？这一章讲清完整流程。

## 从"人肉路由"到"平台自动化"

```
人肉路由阶段（项目早期，手工验证）:
  人类分析需求 → 写 prompt → 粘贴到终端 → 看输出 → 复制结果 → 汇总判断
  人类 = 路由器 + 仲裁者 + 传话筒

平台自动化阶段（当前）:
  人类在聊天室提需求
  → cici咪 分析（MCP 工具创建任务）
  → Engine 自动派发（spawn CLI）
  → agent 执行（cici咪 写代码 / coco咪 写前端 / soso咪 写测试）
  → soso咪 独立 review（发现问题 → 修复 + 补测试）
  → 人类合并 PR
  人类只在需要审批时介入
```

## 每个 AI 输出环节的验证方式

| 环节 | AI 可能犯的错 | 我怎么验证 |
|---|---|---|
| 代码实现 | 逻辑错误、边界漏 | soso咪 独立 review + 单测 + E2E |
| 前端改动 | 样式回归、交互错 | `npm run build` + Playwright E2E |
| 引擎改动 | 死锁、竞态、SQL 错 | 单测 + 集成测试 + review |
| 设计决策 | 方案不合理 | 写 ADR，人类 + soso咪 审查 |
| 文档 | 与实现不符 | 文档同步规则（不一致 = bug）|

## 关键原则

### 1. 谁写代码谁负责，但代码必须被审查

```
不能合并 PR 的条件（铁律）:
  - 没有 soso咪 review
  - 测试没跑过
  - 我（架构师）没有最终把关
  - 人类没有执行合并
```

### 2. 独立审查才有价值

早期我跳过 review 直接合并，多次被用户纠正。soso咪 独立审查发现的真实 bug：
- **死锁**：MCP 审批双 Event，runner 等错了对象
- **XSS**：Markdown 渲染未转义 HTML
- **硬编码**：Stats L3 用假数据占位
- **错位**：SQL 列索引把 status 当 depends_on

**教训：AI review AI 不可靠，必须独立 agent + 测试 + 人类把关。**

### 3. 每步都有数据痕迹

```
每次 agent 调用 → agent_calls 表（token、耗时、输出）
每个任务 → task_table（状态、依赖、prompt）
每个 PR → GitHub（issue 关联、review 记录）
```

面试时可说："项目里每一个 AI 决策都有据可查，我可以指出任意一个 PR 是谁写的、谁 review 的、测试是什么。"

## 面试应对（常见问题）

**Q: 哪些环节你用 AI，哪些不用？**
A: 重复性实现（前端组件、测试用例、CLI 封装）交给 AI；架构决策、任务拆分、最终验收我自己做。AI 是协作者不是决策者。

**Q: 如果 AI 给的方案不对，你怎么发现？**
A: 三个层面：① 写 ADR 时人类审查方案 ② 实现后 soso咪 独立 review ③ 测试（单测+E2E）自动验证。实际发生过：soso咪 发现我写的审批逻辑会死锁，我修复后补了测试。

**Q: 离开 AI 你还能独立完成吗？**
A: 能。核心架构（进程管理、事件模型、数据库设计）是我设计的；AI 负责具体实现。面试中被问到的每个技术点我都能脱稿讲（见 `06-self-check.md`）。

**Q: 你怎么防止 AI 代码污染项目？**
A: 铁律 + 工具：① 没有 review 不能合并 ② 测试不过不能合并 ③ `git diff` 审查每个改动 ④ 数据库不进 git ⑤ 所有运行时数据可重建。
